# T032 — Форк: вендоринг рендер/ввод-зависимостей (wgpu, font-kit, xim-rs, reqwest, scap)

**Приоритет:** P3 — сознательно отложенный хвост T030, не блокер ничего
текущего. Заводится, чтобы не потеряться, не чтобы стартовать сейчас.
**Скоуп:** `Source/`. Правки в `Source/gpui*` **разрешены** — см. Стену 1
T030, она действует и здесь: на форке висят четыре проекта.
**Предшественник:** T030 (`docs/orchestration/tasks/active/T030-zed-tails-in-graph.md`),
раздел «Не в скоупе» — эти пять крейтов туда сознательно не включены,
это решение подтверждено архитектором повторно 2026-08-08 (не тащить
всё за один заход).

## Что в графе

Пять крейтов резолвятся с `git+https://github.com/zed-industries/...` —
но, в отличие от тройки T030 (`http_client`/`util_macros`/`gpui_zed_util`,
zed-внутренние), это **форки сторонних библиотек** с зафиксированным rev:

| Крейт | Что это | Откуда тянется | Объявлен в |
|---|---|---|---|
| `wgpu` | рендер-бэкенд | `zed-industries/wgpu.git` `357a0c5` | `Source/Cargo.toml:88` |
| `font-kit` (`zed-font-kit`) | шрифты | `zed-industries/font-kit` `94b0f28` | `Source/gpui/Cargo.toml:123`, `gpui_wgpu/Cargo.toml:38` |
| `xim` (`xim-rs`) | ввод (X11 IME) | `zed-industries/xim-rs.git` `16f35a2` | `Source/gpui_linux/Cargo.toml:130` |
| `reqwest_client` | HTTP-клиент | `zed-industries/zed` `876ec5a` | `Source/Cargo.toml:152` |
| `scap` (`zed-scap`) | захват экрана | `zed-industries/scap` `4afea48` | `Source/Cargo.toml:150` |

`http_client` из T030 тянет обычный `util` — здесь замена куда рискованнее:
подмена `wgpu` или `xim-rs` — это смена рендерера/ввода, не просто смена
адреса гит-репозитория. Ошибка здесь не «не собралось», а «собралось и
рисует неправильно» — молчаливый регресс, который T030-метрика (счётчик
zed-крейтов) не ловит.

**Явно вне скоупа:** `gpui_macos` — не нужен (Linux-only проект).
`gpui_windows` — интересен на будущее, но не тестируется здесь; остаётся
на git до отдельного решения, не трогать в этом тикете.

## Порядок, по возрастанию риска

**Шаг 0 — снять живьём, что реально нужно.** Для каждого из пяти:
версия, фичи, которые мы включаем (`cargo tree -e features`), и —
критично для `wgpu`/`font-kit`/`xim-rs` — **чем zed-форк отличается от
апстрима** (`git log upstream..zed-fork` или diff по тегу). Если разница
— пяток патчей, вендоринг дешёвый. Если форк разъехался далеко —
вендоринг означает взять на себя поддержку целой библиотеки.

**Шаг 1 — `reqwest_client`.** Вероятно проще всех: обёртка над `reqwest`
(crates.io), не движок. Кандидат на первый шаг.

**Шаг 2 — `scap`.** Захват экрана, используется только за `cfg`/optional
фичей (`scap?/x11`, `optional = true` в манифестах) — если Chronos-FM
эту фичу не включает, вендоринг можно отложить дальше без вреда;
проверить это первым делом.

**Шаг 3 — `font-kit`.** Средний риск: явно версия `0.14.1-zed`, т.е.
zed уже публиковал форк как отдельный пакет — вендоринг может свестись к
`path`-депу на уже существующий форк, а не к копированию исходников.

**Шаг 4 — `xim-rs`.** Только Linux/X11 ввод (`gpui_linux`) — сузить
диff до IME-специфики.

**Шаг 5 — `wgpu`.** Самый дорогой и рискованный: ядро рендера. Не
начинать без явного запроса — даже в рамках этого тикета к нему нужен
отдельный заход с собственными базовыми линиями и, вероятно, визуальным
регрессом на живых кадрах (не только `cargo check`).

## Стены

**Стена 1 — соседи.** Те же четыре потребителя `Source/gpui`, что в
T030 — Стена 1: ChronOS, greeter Chronos-lm, Chronos-FM, Chronos-IDE.
Базовые линии до и после **каждого** шага, не только в конце:

```bash
cargo check --workspace --manifest-path ChronOS/Cargo.toml
cargo check --workspace --manifest-path Chronos-lm/Cargo.toml
cargo test  --workspace --manifest-path Chronos-FM/Cargo.toml   # эталон 294 passed
cargo build -p gpui-component-story                              # из Source/gpui-component
```

**Стена 2 — рендер/ввод не проверяются компилятором.** `cargo check`
зелёный ничего не говорит о том, рисует ли `wgpu`-вендоринг так же. Для
шагов, трогающих `wgpu`/`font-kit`/`xim-rs`, приёмка требует **живого
кадра** (grim) до и после, не только зелёной сборки — тот же стандарт,
что в T029.

**Стена 3 — лицензия.** Как в T030 Стена 3: происхождение в
`Source/NOTICE` + `PATCHES.md` рядом с каждым вендоренным крейтом.

**Стена 4 — шаги независимы, коммиты раздельные.** Как в T030 Стена 2.
Разрешено остановиться после шага 1 или 2 и оставить `wgpu` на git
сколь угодно долго — это не провал тикета.

**Стена 5 — не начинать без явного запроса пользователя.** Это файл
для очереди, не команда на старт. Архитектор решит, когда и с какого
шага заходить.

## Приёмка

- По каждому пройденному шагу: diff zed-форка от апстрима (Шаг 0),
  решение вендорить/отложить и почему.
- Для шагов 3–5 (рендер/ввод) — живой кадр до/после, не только сборка.
- Базовые линии всех четырёх потребителей до и после каждого шага.
- Записи в `NOTICE`/`PATCHES.md` для всего перенесённого.
- Явно названо, что осталось на git и почему.
