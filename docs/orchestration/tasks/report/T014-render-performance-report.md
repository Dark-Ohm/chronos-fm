# T014 — отчёт расследования: рендер-перформанс / 144 fps

**Приоритет:** P1
**Исполнитель:** WorkBuddy (headless worker)
**Статус:** РАССЛЕДОВАНИЕ. **Правок коду нет** (тикет запрещает оптимизации до
замера). Ниже — инвентаризация форка, статический разбор горячих путей и план
замера для архитектора. Числа «до» по кадру НЕ получены — они требуют живой
GUI-машины (см. «Честный итог»).

---

## Шаг 0. Дешёвые проверки окружения

### 0.1 Адаптер — уже установлено (не повторять)
Vulkan на дискретной RTX 3070, софт-рендера нет (см. тикет, п.5). Повторная
проверка не нужна.

### 0.2 Present mode — проверено по коду форка (вместо запуска)
- В коде приложения **нет** ни одной установки `preferred_present_mode` /
  `PresentMode` / `vsync` (`grep` по `crates/` пуст). Значит используется
  платформенный дефолт.
- Форк `../Source`: на **Wayland** окно выставляет
  `preferred_present_mode: Some(wgpu::PresentMode::Mailbox)`
  (`gpui_linux/src/linux/wayland/window.rs:571-572`) — «Prefer Mailbox to avoid
  blocking». Mailbox — triple-buffering, представляет самый свежий готовый кадр
  на vsync **без блокировки** приложения. То есть на стороне кода **нет
  искусственного потолка** до частоты обновления монитора.
- Дефолт рендерера — `Fifo` (VSync) только если платформа не даёт Mailbox
  (`gpui_wgpu/src/wgpu_renderer.rs:432-435`). На Wayland выбирается Mailbox.

**Вывод 0.2:** код не зажимает fps к 60. Если монитор реально 144 Гц и
композитор не накладывает доп. потолок — 144 fps физически достижимы.

### 0.3 Частота монитора + vsync/композитор — НЕ измерено (нужна живая машина)
На headless-воркере `hyprctl monitors` / `wlr-randr` недоступны, а бинарь
собрать нельзя из-за **ashpd-блокера** (см. T016-report §«Блокер сборки»).
Команды для архитектора:
```bash
hyprctl monitors            # ищем "refreshRate" / "hz" целевого монитора
wlr-randr                   # альтернатива для wlroots
vulkaninfo | grep -i present # поддерживаемые PresentMode (Mailbox?)
WAYLAND_DEBUG=1 chronos-fm   # посмотреть frame callbacks / пейсинг композитора
```
Если монитор в режиме 60 Гц ИЛИ композитор (Hyprland/Niri) капает приложение к
60 — 144 fps **физически недостижимы** независимо от кода. Это главный
кандидат «снаружи кода», который тикет велел проверить первым.

## Шаг 1. Инвентаризация инструментации форка (проверено ДО того, как городить своё)

- **Встроенного профайлера нет**: `tracy` / `puffin` в форке отсутствуют;
  `tracing::` span-ов вокруг paint/present в `gpui_wgpu` нет.
- **Троттлинг кадров** в `gpui/src/window.rs` (`on_request_frame` →
  `min_frame_interval`):
  - активное окно → `None` (без потолка, идёт на частоте дисплея),
  - неактивное (не в фокусе) → ~30 fps (`33333µs`),
  - тепловой режим `Serious|Critical` → ~60 fps (`16667µs`).
  То есть для **активного** окна потолка нет — подтверждает 0.2.
- **Внутренний тайминг** `last_frame_time: Rc<Cell<Option<Instant>>>` есть
  (`gpui/src/window.rs:1360,1496,1509`), но НЕ выставлен наружу публичным
  API — прочитать из приложения без патча нельзя. Поэтому замер — через
  внешний `perf`, а не через «дёрнуть cx.frame_time()».

### План замера (для архитектора, 3 режима: покой / скролл / hover)
1. Собрать релиз **с символами** (иначе стек пуст):
   ```bash
   CARGO_PROFILE_RELEASE_DEBUG=1 CARGO_PROFILE_RELEASE_STRIP=none \
     cargo build --release
   ```
   (`[profile.release]` сейчас `strip="debuginfo"`, `opt-level=3`,
   `lto="thin"` — символы добавляем только для замера.)
2. Запустить релизный бинарь (`~/.local/bin/chronos-fm` уже симлинк на
   `target/release/`), открыть папку ~114 items.
3. `perf record -F 1000 -g -p $(pidof chronos-fm) sleep 10` в каждом из 3
   режимов, затем `perf report --hierarchy` (или `hotspot`/`inferno`).
4. Альтернатива/дополнение — временный HUD часто��ы кадра (после шага 1,
   опционально): `window.request_animation_frame()` + `Instant::now()` delta →
   stderr. **Не делать до замера** (тикет запрещает правки до цифр).
5. Результат — таблица «что сколько занимает в кадре» по трём режимам +
   фактический режим монитора + адаптер. **Без этой таблицы к шагу 2 не
   переходить.**

## Честный итог

- **Кодовая сторона:** нет хард-капа fps (Mailbox на Wayland, нет throttle при
  активном окне), нет профайлера в форке (мерить через `perf`), единственный
  подтверждённый оверхед — `get_shortcuts` 4 stat/рендер (малый, чинит T015).
- **Внешняя сторона (главный кандидат):** реальная частота монитора и политика
  vsync композитора **не измерены** — они решают, достижимы ли 144 fps вообще.
  Если монитор 60 Гц или композитор капает к 60 — цель недостижима независимо
  от кода.
- **Числа «до» по кадру отсутствуют.** Заявить «144 fps достижимо/нет» без
  живого замера нельзя — это прямо запрещено тикетом («не догадки»).
- **Блокер среды:** в этом окружении бинарь не собирается (ashpd-конфликт), и
  GUI/монитор недоступны → замер физически можно сделать **только на машине
  архитектора**.

## Следующие шаги (для архитектора)

1. Выполнить Шаг 0.3 (монитор + vsync) и Шаг 1 (таблица frame-time в 3 режимах)
   на живой машине. Если упирается в 60 Гц/композитор — зафиксировать и
   закрыть как env-limited (не чинить код).
2. Если монитор 144 Гц и композитор не капает, а кадр всё равно тяжёлый —
   брать топ из `perf report`, чинить точечно (первым — `get_shortcuts`,
   уже в T015), и замерять повторно.
3. T015 перепишет сайдбар — `get_shortcuts` уйдёт из горячего пути само собой;
   стоит координировать, чтобы не дублировать правку.
