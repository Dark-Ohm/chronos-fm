# T014 — Рендер-перформанс: довести до 144 fps

> ## Статус (2026-08-09, чекпоинт #8)
>
> **T014-A ACCEPT** (layout memoization in Source/gpui). T022/T033/T015 done.
> AFTER packet accepted. Umbrella stays open until 144 fps or measure-proven
> unreachable.
>
> **Next product:** T010-B (git branches/diff). **Next fork QA:** T029.
> Optional: live hover AFTER-A on release binary.

**Приоритет:** P1 — цель проекта («blazing fast gpui file manager»), сейчас
не выполняется. Не блокер функционала, но блокер daily-driver-ощущения.
**Статус (2026-08-09, чекпоинт #6):** **T022 partial-accept + T033
partial-accept.** Цикл watcher↔self-index **мёртв архитектурно**:
за 4 минуты idle на новом бинаре наш consumer (`process_changes`)
вызвался **0 раз** из watcher'а. `merge_thread_0` всё ещё
держит ~30 % CPU в первые 4 минуты, но это tantivy's own
cold-start consolidation мелких сегментов от прошлых T014 runs —
не loop. Полный поток: см. `report-log/T033-kill-watcher-self-index-feedback-loop-report.md`.
T022 чекпоинт #5 ранее закрыл `WATCHER_DEBOUNCE = 5 s` + Part C audit
(no-op). Quality gate по обоим тикетам: green (89/89 + 87/87 passed
соответственно). **Следующий шаг:** AFTER single packet (idle + scroll
+ hover) на stabilised index, не на cold-start — один прогон после
того, как tantivy сольёт ~14 мелких сегментов в 1-2 (это происходит
само через несколько минут на hot relaunch). Решение по
**T014-A** (layout memoization) принимается по post-T033 цифре
scroll taffy. Вариант **B** — без отдельного разговора.

**Что показал замер** (3×10 с, `perf -F 1000 -g`, release с символами):
монитор 2560×1440 @ 144 Гц, present mode Mailbox, VRR выкл. — потолок
не внешний. Узкое место: `taffy` пересчитывает всё flexbox-дерево
каждый кадр (~40 % в покое, **~70 % при скролле**, ~65 % при hover),
плюс debouncer `notify-rs` ест ~30 % CPU в покое.

**Выбор сделан (2026-08-06):** идём рекомендованным путём — **D + C**
вынесены в **T022** и готовы к раздаче. Вариант **A** (layout
memoization в форке gpui) — следующим шагом, решение принимать по
цифрам «до/после» из отчёта T022. Вариант **B** остаётся открытым
вопросом и без отдельного разговора не берётся.

T014 остаётся зонтичным тикетом цели «144 fps» и закрывается только
когда цель достигнута либо признана недостижимой по замеру.

**Варианты из отчёта (для истории решения):**
- **D** — поднять debounce-таймаут watcher'а (1 строка, ~30 % CPU в
  покое, риск минимальный)
- **C** — уплощить дерево элементов в рендере (низкая сложность,
  ~15–25 % меньше taffy-нод)
- **A** — layout memoization в форке gpui: хешировать стили, пропускать
  `compute_layout` при совпадении (~80 строк, самый большой выигрыш при
  разумной сложности)
- **B** — reuse taffy-нод между кадрами (~200 строк, меняет
  фундаментальный инвариант GPUI, нужен полный регресс форка)

Рекомендация отчёта: D + C сейчас, A следующим шагом, B — только с
отдельным решением.

**Ловушка при работе с этим тикетом:** голый `cargo build --release`
бинарь **не собирает** — GUI-крейты вне `default-members` в корневом
`Cargo.toml`. Нужен `cargo build --release -p chronos-fm`, иначе замер
уйдёт в старый артефакт. Проверено на своей шкуре 2026-08-06.
**Источник:** живой прогон 2026-08-06 (скриншот `/home/neo`, 114 items),
жалоба пользователя: «работает на 20+/- фпс, а нам нужен blazing fast
144fps gpui file manager».

## Что уже установлено эмпирически (не повторять эту работу)

1. **Корень первой волны найден и устранён** — запускался debug-бинарь
   (`~/.local/bin/chronos-fm` был симлинком на `target/debug/`, 981 МБ).
   В `Cargo.toml` не было `[profile.dev]` вообще → все зависимости
   (`gpui`, `wgpu`/blade, шейпинг шрифтов, layout) собирались на
   `opt-level = 0`. Исправлено коммитом `58e0928`: зависимости на
   `opt-level = 3` без debug-инфо, свой код на `opt-level = 1`.
   Симлинк перевешен на `target/release/chronos-fm` (44 МБ).
2. **Результат после перехода на release: «не летает, но гораздо
   лучше»** (оценка пользователя, живьём). То есть под множителем
   debug-сборки есть **вторая, настоящая проблема** — её и надо найти.
3. **Список УЖЕ виртуализирован** (`v_virtual_list`, `list.rs:71`) —
   114 строк не рендерятся все. Это не узкое место, не «чинить» повторно.
4. **Подтверждённая мелочь**: `get_shortcuts()` (`sidebar.rs:106-132`)
   делает 4 синхронных `Path::exists()` (stat) **на каждый рендер**
   сайдбара. Это I/O в горячем пути. Малый вклад, но убрать (кэшировать)
   надо — см. также T015, который переписывает сайдбар.
5. **Адаптер проверен живьём (2026-08-06) — софт-рендера НЕТ.** Лог
   запуска релизного бинаря:
   ```
   Found 2 GPU adapter(s):
     - NVIDIA GeForce RTX 3070 (vendor=0x10de, device=0x2484,
       backend=Vulkan, type=DiscreteGpu)
     - NVIDIA GeForce RTX 3070/PCIe/SSE2 (backend=Gl, type=Other)
   Selected GPU (passed configuration test): NVIDIA GeForce RTX 3070 (Vulkan)
   ```
   Дискретная карта с Vulkan выбрана корректно, llvmpipe/софт-фоллбэка
   нет. **Гипотеза «софтверный рендер» закрыта — не проверять повторно.**
   Недостающие кадры сидят либо в коде рендера, либо в vsync/композиторе.

## Что нужно — строго в этом порядке

### Шаг 0. Дешёвые проверки окружения ДО профайлера

- ✅ ~~Какой graphics-адаптер реально выбран~~ — **сделано, см. п.5
  выше: Vulkan на дискретной RTX 3070, софт-фоллбэка нет.**
- **Реальная частота монитора**: если он в 60 Гц-режиме, 144 fps
  физически недостижимы. `wlr-randr` / `hyprctl monitors` — записать
  фактический режим в отчёт.
- **Vsync/композитор**: выяснить, ограничивает ли композитор частоту
  кадров приложения, и какой лимит выставлен. С учётом того, что адаптер
  уже исключён, это главный оставшийся кандидат «снаружи кода» — проверять
  первым.

Если проблема здесь — дальше не копать, зафиксировать и закрыть.

### Шаг 1. Замер, а не догадки

- Снять **frame time** (не «ощущение fps») в трёх режимах отдельно:
  покой (ничего не двигается), скролл списка, hover по строкам.
- Профилировать **release-сборку**, но `[profile.release]` содержит
  `strip = "debuginfo"` — для профайлера собрать временный профиль с
  символами (`debug = 1`, `strip = "none"`), иначе стек будет пустым.
- Инструмент на выбор исполнителя (`perf record`/`perf report`,
  либо встроенная в gpui/blade инструментация, если она есть в форке
  `../Source` — проверить перед тем, как городить своё).

**Результат шага 1 — таблица «что сколько занимает в кадре».** Без неё
переходить к шагу 2 запрещено.

### Шаг 2. Только после замера — гипотеза и точечный фикс

Ни одной оптимизации «на всякий случай». Каждая правка — против
конкретной строки из замера, с повторным замером после.

Кандидаты для проверки (это **подозреваемые, не диагноз** — не
оптимизировать, пока замер не подтвердит):
- частота ре-рендера: не дёргает ли что-то `cx.notify()`/
  `NotifyGlobalObservers` постоянно (в т.ч. `observe_global::<DeviceStore>`
  из T008, hotplug-watcher);
- стоимость preview-панели;
- тени/скругления/`elevated_card` — сколько стоят слои;
- иконки и шейпинг текста на строку.
