# T024 — Порт остатков рабочих паттернов из ChronOS (rejected/, notes/, по-проектные скиллы)

**Приоритет:** P3 — housekeeping, не пользовательская функциональность.
**Роль:** решение архитектора (что портировать, а что осознанно не портировать).
**Статус (2026-08-09):** **RATIFIED** — все 4 решения приняты архитектором и записаны в `DECISIONS.log`.

| # | Пункт | Решение |
|---|-------|---------|
| 1 | `rejected/` | **Портировать** — создан, T011 REFUTED перенесён |
| 2 | `notes/` | **Не портировать** — покрыто `.workbuddy/memory/` |
| 3 | `MIGRATION.md` | **Не портировать** — FM на per-task с начала |
| 4 | Скиллы | **По потребности** — без оптового переноса |

Тикет готов к переносу в `done/`.
**Источник:** раздел «Контекст: порт рабочих паттернов уже ≈60% сделан» в T023
(аудит 2026-08-07) + прямое решение пользователя завести отдельный тикет.

## Суть

T023 закрывает empty-state решение и механизм записи решений
(DECISIONS.log + ADR 0010). Этот тикет — оставшиеся ~40% пробелов порта
рабочих паттернов из ChronOS. По каждому пункту фиксируется явное
решение «портировать / не портировать / портировать по потребности» —
без молчаливого пропуска.

## Пункты

### 1. `rejected/` — кладбище отклонённых/заменённых отчётов

**ChronOS:** `docs/orchestration/tasks/rejected/` — 27 файлов: отчёты с
вердиктом REJECTED (суффикс `-REJECTED.md`, напр. `T116-…-REJECTED.md`),
superseded-тикеты (`T113-…-superseded-by-T177.md`), убитые тикеты
(`T189-scenes-tab-killed.md`), даже сфабрикованные отчёты
(`T181-slice-4-smoke-report-fabricated*.md`). Отдельное место, чтобы
не путать с принятыми и не мусорить в `report-log/`.

**Chronos-FM:** `rejected/` нет. Сейчас оспоренные отчёты остаются в
`report/` с эрратой (T011: REFUTED + эррата поверх ложных утверждений
верификации).

**Вопрос:** заводить `rejected/` и переносить туда REFUTED/REJECTED-
отчёты по факту (T011?) — или эррата в `report/` уже достаточна?

**Предложение:** портировать конвенцию (директория + суффиксы) как
финальный приют для REFUTED/REJECTED/superseded; эррату в исходном
отчёте сохранять, в `rejected/` класть ссылку-дубликат. Решает
архитектор.

### 2. `notes/` и session-knowledge

**ChronOS:** `notes/` — ad-hoc архив (отчёты, скриншоты, WIP-файлы,
superseded-материалы); `session-2026-07-25-knowledge.md` — дамп знания
сессии.

**Chronos-FM:** функцию session-knowledge уже покрывает
`.workbuddy/memory/` (MEMORY.md + 2026-08-05.md). Отдельного `notes/` нет.

**Вопрос:** заводить `notes/` по образцу ChronOS или не плодить дубль
`.workbuddy/memory/`?

**Предложение:** НЕ заводить `notes/` (дублирует `.workbuddy/memory/`);
session-knowledge конвенцию считать покрытой. Решает архитектор.

### 3. `MIGRATION.md`

**ChronOS:** `docs/orchestration/tasks/MIGRATION.md` — T-ID-леджер
одноразовой миграции per-agent → per-task (2026-07-22). Исторический
артефакт, не живая конвенция.

**Chronos-FM:** FM не проходил такой миграции — сразу per-task учёт.

**Предложение:** не портировать, закрыть пункт как «не нужно». Решает
архитектор (зафиксировать явно, чтобы вопрос не всплывал повторно).

### 4. По-проектные скиллы ChronOS — портировать по потребности

Не перенесены в FM (11): `rtl-text-rendering`,
`tokio-coop-budget-on-main-thread`, `hot-lib-reloader`,
`evaluating-hot-reload-solutions`, `eye-candy`, `gpui-component-in-chronos`,
`chronos-gpui-popup`, `chronos-bar-config`, `chronos-llm-backends`,
`hermes-acp-tool-completed`, `check-proofs.sh` (скрипт).

**Как решать:** по мере появления в FM задачи, которой скилл
соответствует — сверить с исходником в ChronOS и портировать с
адаптацией. Кандидаты, вероятно релевантные FM (gpui-проект с tokio в
services): `tokio-coop-budget-on-main-thread`, `rtl-text-rendering`
(если появится RTL-контент).

**Предложение:** правило «по потребности», без оптового переноса.
